# v0.2.0

## Supervising, bounded-context teams

This release adapts five ideas from DeepSeek Harness's *Super-agent* design to the AgentTeams plugin: an independent watchdog, a captain that stays in the Router role, bounded context via digest/recall, member progress heartbeats, and captain report batching.

### Independent watchdog (P0-2)

- A host-side loop scans active teams every `watchdog.intervalSeconds` (default 60s) and raises alerts for:
  - **stalled** attempts: a claimed/in-progress task with no progress heartbeat for `watchdog.stallSeconds` (default 30m);
  - **retrying**: a task that has consumed `watchdog.maxAttempts` (default 4) attempts without completing;
  - **repeat-message**: the same sender → recipient → content repeated `watchdog.repeatThreshold` (default 3) times within `watchdog.repeatWindowSeconds` (default 10m).
- Alerts are persisted in `team.json` under `watchdog` (up to 20, first-seen timestamps preserved) and appear in `deers_team_status` and `deers_team_digest`.
- The captain is woken once per newly raised alert with a bounded prompt. The watchdog never mutates task state: it reports, the captain (or the human) decides.
- Set `watchdog.enabled: false` to disable, `watchdog.notifyCaptain: false` to keep alerts without waking the captain.

### Captain stays in the Router role (P0-3)

- New config `captainMayImplement` (default **false**). With the default, captain takeover of `implementation` / `repair` tasks is rejected by both the model-facing `deers_team_reassign_task` and the Web panel reassign operation, with an error that points at assigning the task to a member.
- Non-implementation takeover (review, integration, ad-hoc `work`) and user-requested rescues remain possible; enable `captainMayImplement: true` when the captain really must implement.
- The captain protocol now states the Router-role policy explicitly.

### Bounded context: digest and recall (P1-4)

- `deers_team_digest` returns a compact, length-bounded summary: member/task counts, active tasks with heartbeat age and progress, blocked and failed tasks, blackboard highlights, watchdog alerts, lead-time metrics and recent messages.
- `deers_team_recall` fetches exact detail by id: a task's full contract/output/evidence, a mailbox message, or a blackboard entry. At most 10 refs per call.
- The captain protocol now prefers the digest on routine turns and uses recall only when an id matters; `deers_team_status` remains the full snapshot.

### Progress heartbeats for long tasks (P1-5)

- New member tool `deers_team_progress` (task_id + current attempt_id + optional percent/note) records `task.progress.updatedAt` without changing task status. The watchdog uses it to distinguish "still working" from "stalled".
- Progress is shown in `deers_team_status` task rows and in `deers_team_digest` active rows; members may keep calling it during long test/build/browse steps.

### Captain report batching (P1-6)

- Member reports to the captain are coalesced within `routerBatchWindowMs` (default 1200ms): an idle captain wakes once for a burst, a running captain receives the steer immediately. Reports stay durable in the mailbox; a failed live steer only delays the wake.
- `routerBatchWindowMs: 0` disables batching.
- Together with the digest, this cuts the number of captain wake-ups and the size of each routine captain read.

### Configuration

```yaml
- id: deers-agent-team
  config:
    captainMayImplement: false      # Router role by default
    routerBatchWindowMs: 1200       # 0 disables report coalescing
    watchdog:
      enabled: true
      intervalSeconds: 60
      stallSeconds: 1800
      repeatWindowSeconds: 600
      repeatThreshold: 3
      maxAttempts: 4
      notifyCaptain: true
```

### Compatibility

All new state fields (`task.progress`, `watchdog`) are optional; existing team records load unchanged. New tools are additive and member-visible except where noted. The existing quality gates, attempt capabilities, blackboard and Web surfaces are unchanged.
